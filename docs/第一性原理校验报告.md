## 二、需完善（缺什么）

判据：**目标要求「研究」，但系统只提供「浏览」**。以下每项都对应研究闭环的一个断点。

### 2.1 【P0】溯源：作业没有稳定身份，无法引用、无法复核

**问题**：一条作业在系统里只有内部 `id`（UUID），没有对外可引用的标识。灯箱里的「打开原站」只能回到榜单页（`NOTICE.md:38` 已自述上游没有单条作业的公开深链）。研究结论一旦写下，「这条结论依据哪条作业」无法回指。

**证据**：
- `webui/js/explore-board.js:111-117` 的 `matches()` 只有批次、比例、sref、搜索四个维度，**无 id 维度**；
- `config/explore.yaml` 顶层只有 `source` / `batches` / `aspects` / `jobs`，`source` 是**批次级**的 `url`（`https://www.midjourney.com/explore?tab=top`），无逐条 URL；
- 深链机制只用于筛选状态（ADR-0010），且 `webui/js/workbench.js:60-63` 的 `readHash()` **只认页签 id**（只匹配 `TABS` 里显式写死的 `artists` / `explore` 两个，词库的 4 个分类靠 `VOCAB_CATEGORIES.map` 展开），传 `#explore?job=xxx` 会被丢弃。

**要补什么**：给作业一个**本项目自有的稳定引用键**（例如 `job` 的 id 前 8 位 + 提示词前若干字的规范化哈希），支持 `#explore?job=<key>` 直达灯箱；结论记录引用该键。

**为什么这是 P0**：没有它，「记录」和「对照」两段都无法成立 —— 结论挂不到证据上。

**修法与验证（2026-11-10 落地，第 5 步）**：

#### 键的构造

    <样本标识前 8 位>-<提示词规范化哈希前 4 位>

两段各有分工：

- **前 8 位**标识「是哪一条」。上游标识一次生成、跨批次重采不变，且 `tools/collect-explore.ts` 的 `mergeJobs` 按 id 去重（base 优先），所以同一条样本在快照中永远只有一条、批次取首次采集那天 —— 键不随重采搬家。
- **后 4 位**标识「内容是否变过」。若上游某天改了同一条样本的提示词正文，哈希会变 → 键会变 → 引用旧键的人会发现内容对不上，而不是拿到一条被悄悄改写过的样本。

#### 为什么不用别的方案（实测数据）

| 候选键 | 实测结果 | 判定 |
| --- | --- | --- |
| 纯提示词哈希 | 971 条里 **34 组碰撞**（社区大量重复提示词：同一句模板被不同作者反复用） | **不可用** —— 撞键就等于两条样本互相顶替 |
| 纯 id 前 8 位 | 971 条零碰撞，但 32 bit 在 ~7.7 万条时碰撞概率约 50% | **靠运气**，不靠保证 |
| **id 前 8 位 + 哈希前 4 位** | 971 条零碰撞，有效位宽 48 bit | **采用** —— 加上构建期零碰撞断言，不靠概率 |

#### 改动

| 位置 | 改动 |
| --- | --- |

#### 深链形态

    #explore?job=<引用键>

与筛选深链（ADR-0010）的分工：筛选深链记「当前筛选状态」，`job` 参数记「正在看哪一条样本」，两者可共存。深链用**相对 `index.html`**，`file://` 与 `http://` 下都成立 —— 深链是给人和笔记用的，粘到别的机器上也能开。

### 2.2 【P0】对照：无法固定变量做归因

**问题**：研究里最常见的动作是「两条作业只差一个变量，判断这个变量是不是主因」。当前系统只能分别浏览、收藏、整条套用。

**证据**：
- 社区作业**原始 prompt 里几乎不含参数**——实测 957 条里只有 8 条含 `--` 串，且这 8 条全是误命中（`--a`、`--massive`、`--stretching`、`--perfect`、`--an`、`--i`、`--the`、`--blue`，全是自然语言里的双连字符），**含 `--sref` 的作业为 0**；
- `sref` 只存在于**独立字段**中（81 条），且该字段在构建期被丢弃（见 3.1）；
- 筛选维度（`explore-board.js:108-118`）不支持按 sref 码值筛选，也不支持按 prompt 片段筛选。

**具体场景（无法完成）**：判断 `--sref 3808026652` 是否单独造成暖色调 → 需要「按 sref 码筛选出全部命中作业」+「按 prompt 片段分组」+「固定其他变量并排比较」。三条全缺。

**要补什么**：① 按 sref 码值筛选（不是只有「只看有 sref」这个布尔开关）；② 按 prompt 片段/关键词做聚类；③ 一个「并排看两条」的对照视图。

### 2.3 【P0】记录：有收藏但没有观察与结论

**问题**：现有的「收藏」只是一个布尔标记，存的是提示词正文的 FNV 哈希 → `'1'`（`webui/js/explore-board.js:23-54`）。它记不住「我为什么收藏它」「我从中看到了什么」。

**证据**：
- `webui/js/core.js:199-208` 的 `saveSession()` 落盘的只有 `selected` / `subject` / `manual` / `params`，**没有任何研究笔记字段**；
- `webui/js/explore-board.js:15` 的 `FAV_PREFIX = 'mj-explore-fav-'` 每个作业一个 localStorage 键 —— 957 条就是 957 个键，无法承载文本，也无法聚合查询；
- 收藏键基于**提示词正文**而非作业 id，而实测有 **34 条提示词重复（涉及 74 条作业）** → 同一条提示词的两次收藏会互相覆盖，**这是确证的语义 bug**。

**要补什么**：把「观察记录」升为**一等数据**：一条作业 ↔ 多条观察（笔记、假设、标签），支持按标签聚合；结论单独一层，指向它依据的作业集合。

**修法与验证（2026-11-10 落地，第 6 步）**：

#### 数据模型

两类实体，两个 store：

| 实体 | 字段 | 索引 |
| --- | --- | --- |
| **观察记录**（`notes`） | `id` / `jobKey` / `body` / `tags[]` / `createdAt` / `updatedAt` | `byJob`（jobKey）、`byTs`（createdAt）、`byTag`（tags，`multiEntry`） |
| **结论**（`conclusions`） | `id` / `title` / `body` / `jobKeys[]` / `createdAt` / `updatedAt` | `byTs`（createdAt）、`byJob`（jobKeys，`multiEntry`） |

两个关键选择：

- **观察记录挂的是引用键（第 5 步的 `<id8>-<hash4>`），不是 UUID** —— 研究笔记要能贴进论文、粘到聊天里、被搜索到；36 个字符的 UUID 做不到。挂键还带来一个额外好处：引用键与样本一一对应，**笔记不会因为重采换批次而失效**。
- **结论用 `jobKeys[]` 指向依据的样本集合，不归属任何一条样本** —— 同一组证据可能支撑多条结论（"这批暖色调都靠 sref" 可以同时是一条构图结论和一条色调结论的依据）。

#### 存储选型：实测而非推测

选型前先用**真浏览器**量了一遍，不是查文档：

| 能力 | 实测结果 | 判定 |
| --- | --- | --- |
| `file://` 下 IndexedDB | 建表 / 读写 / 索引**全部可用**，`isSecureContext = true`，origin = `file://` | 可用 —— 离线红线没破 |
| IndexedDB 容量 | 写入 **20,000 条 1KB 记录（20 MB）未触顶**（无 `quotaError`） | 远超研究笔记的量级 |
| localStorage 容量 | 实测 **5042 KB ≈ 4.9 MB** 即 `QuotaExceededError` | 与报告 4.1 说的"约 5 MB"吻合 |
| `file://` 下跨目录 | 不同路径**共享同一个库**（origin 都是 `file://`） | 4 个 HTML 页可共用一个库 |

选 **IndexedDB** 而非 localStorage 的理由不是"IndexedDB 更大"，而是**第 10 步**要在同一个库上扩展作业/拆解的查询下沉、增量与导出 —— 塞进 localStorage 会在第 10 步被推翻重写。

#### 三个实现细节值得记

1. **IndexedDB 事务不能跨 `await`** —— 规范允许浏览器在 await 让出微任务后自动提交事务，后续 `put` 会抛 `TransactionInactiveError`。所以 `updateNote` / `updateConclusion` 刻意用**「读事务 → 写事务」两步**，每个事务内部同步完成，不依赖脆弱时序。
2. **`researchchange` 用全局事件而不是冒泡** —— 观察记录弹层是**嵌套**在灯箱里的 `mountDialog`，保存按钮的点击**不会冒泡到外层 backdrop**。灯箱里的计数与列表改用 `document.addEventListener('researchchange', ...)` 同步，并在灯箱关闭时 `removeEventListener`（避免每次开灯箱多一个监听器）。
3. **"页签数"断言不能写死** —— 旧断言写死"工作台 6 个页签"，加一个页签就要改一处断言。改为**动态断言**"DOM 里的页签数 == `TABS` 声明的页签数"，以后加页签不用动断言。

### 2.4 【P1】`sref` 断链：源数据有 81 条真值，前端拿到的全是 null ✅ **已修复（2026-11-10）**

**问题**：`config/explore.yaml` 里 **81 条作业带真实 `sref` 字段**（63 个互不相同的字段值，其中 20 条是多码；把多码拆开后共 **96 个唯一风格码**），但构建期被硬编码抹成 `null`。

**证据**：
- `scripts/build-webui-data.mjs:121-122`（修复前）：

  ```text
  // 源数据（prompt / paramTail / tags）均未采集 sref；原型样本里那 2 个值是杜撰，不继承。
  sref: null,
  ```

  **这条注释是错的** —— `config/explore.yaml` 里 81 处 `sref:` 是真实采集值；
- 注释后半句本身也对：**2 个值确实是杜撰** —— ADR-0017:58 记原型样本里的 `3808026652` / `3414761933` 查无出处。但实测这两个码**确实存在于源数据**（`config/explore.yaml:4168` 有 `3414761933`），说明它们被上游采到了，只是当时没认出来；
- 后果：`webui/js/explore-board.js:113` 的 `if (ui.srefOnly && !j.sref) return false` **恒真** → 「只看有 sref」筛选永远空集；
- `webui/js/explore-board.js:176-178` 因此改渲染为「源数据未采集 sref」chip —— **界面在如实说谎**（不是杜撰值，是漏掉了已有的真值）；
- `scripts/verify-webui.mjs:104` 的断言 `check('sref 未杜撰（源数据未采集）', data.sref === 0)` **把这个 bug 固化成了验收标准**；

**要补什么**：构建期改为透传 `j.sref`（缺失则为 `undefined`），并同步修正 verify 断言与 ADR-0017 的表述。这一条是**改动最小、收益最大**的修复。

### 2.5 【P1】拆解质量分层不可用：889 条规则兜底与 53 条精拆混在一起

**问题**：942 条拆解里，**889 条是规则解析**（确定性关键词匹配），53 条是 LLM 精拆。两者精度差异大，但界面上只靠一个角标文字区分。

**证据**：
- `config/explore-decomposed.yaml:5`：`"model": "混合：3 条 WorkBuddy 手工精拆 + 50 条逐条精拆（LLM 语义判断） + 889 条规则兜底"`；

- `scripts/verify-webui.mjs:155-160` 的角标映射只区分三种来源文案。

**要补什么**：按拆解来源分层筛选（精拆 / 规则），研究结论默认只采信精拆层。

### 2.6 【P1】词库与社区数据之间零通路：手工先验无法被社区数据检验

**问题**：`config/prompts.yaml` 的 156 条词库与 957 条社区作业是**两套互不相通的文本**。没有任何代码路径让「社区里高频出现的表述」与「词库里的条目」相遇。

**证据**：
- 词库数据在 `webui/js/data-vocab.js`，社区数据在 `webui/js/data-explore.js`，两者**无任何交叉引用**；
- `config/prompts.yaml` 的 `artists` 分类下 23 条手写艺术家条目，**全部并入 `data-artists.js`**（实测 23/23 按规范化英文名匹配命中），但**其中 20 条的预览图在 `webui/assets/artists/` 里不存在**（实测命中 3/23），且这 23 条在产物里 `preview` 为 `null`（被上游 Midlibrary 数据覆盖）；
- 没有任何「候选词条」概念 —— 社区 prompt 里出现 `light and shadow`，词库里没有，没人知道该把它记下来。

**要补什么**：单向通路 —— 从社区样本抽出**候选词条**（出现频次 + 原始出处），人工/对照检验后并入词库。词库是**待验证的假设集**，社区数据是**证据集**，两者要能对质。

### 2.7 【P2】批次语义与真实时间不一致：954/957 条的批次键 ≠ 实际入队日期

**问题**：`batch` 字段被当作「日期」用（批次下拉写「11-05」），但它实际是**首次采集日**。

**证据**（实测）：954/957 条的 `batch` 键与 `enqueueTime` 换算出的日期不一致。例如批次 `2026-11-05` 下 174 条，实际入队日期横跨 **2026-10-06 到 2026-11-02 共 28 个不同日期**；批次 `2026-11-01` 下的作业实际入队于 `2026-10-31`。

**根因**：`tools/collect-explore.ts:231-236` 的 `mergeJobs()` 注释说得很清楚 —— 「批次取第一次采集到的那天，历史批次才稳定」。这是**正确的设计**，但下游把它当成了「作业生成日期」。

**要补什么**：术语上区分「采集批次」与「生成时间」。`enqueueTime` 已全量存在（957/957 非空），时间维度的真实查询能力是**现成的**，只是口径没对齐。

### 2.8 【P2】缺口：参数维度在社区数据上完全失效

**问题**：作业的 `version` 字段实测 **957/957 全是 `'8.2'`**，参数段实测只有 8 条疑似命中且全是误命中。也就是说，**社区数据无法支撑任何参数维度的研究**。

**证据**：
- 8 条误命中样例：`--a`、`--massive`、`--stretching`、`--perfect`、`--an`、`--i`、`--the`、`--blue`；
- 拆解数据里的 `paramTail` 是**拆解工具推断出来的**，不是社区作者写的。

**要补什么**：要么承认「社区数据的参数维度不可研究」（写进术语与界面说明），要么在采集侧补参数（上游 API 的 `prompt` 对象里有结构化参数，见 `tools/collect-explore.ts` 的 `ExploreApiJob` 类型）。**不要用推断值冒充真实值** —— 当前 `paramTail` 的 `model` 标记已经区分了来源，界面应同步。

### 3.1 【P0】拆解输出链：多个工具写同一个文件，格式互斥 ✅ **已修复（2026-11-10）**

**冲突是硬的**：`scripts/build-webui-data.mjs` 用 `JSON.parse` 读这个文件。实测 `yaml.dump` 的输出 `JSON.parse` 直接抛错（`Unexpected token 'j', "jobs:\n - jobId: a\n" is not valid JSON`）→ **跑一次 `npm run decompose:explore` 就会让构建链炸掉**。

**要合并什么（初稿）**：拆解输出只留一个写者，格式统一为 JSON。

**修法与验证（2026-11-10 落地）**：

**先对齐了「单一写者」的含义**。三个写者**职责互补，不是重复实现** —— `decompose-explore.ts` 走 LLM 语义判断、`rule-decompose.mjs` 是确定性规则兜底（当前 889 条数据的唯一来源）、`merge-fine-parts.mjs` 合并人工逐条精拆分片。砍掉任何一个都会丢能力。因此本步**不砍写者，只统一格式与契约**：

| 位置 | 改动 |
|---|---|
| `tools/decomposed-format.mjs`（新增） | 派生文件格式契约的**单一来源**：导出 `describeSources()`（如实统计各来源条数）与 `serializeDecomposed()`（**纯 JSON**，无注释头）。配 `decomposed-format.d.ts` 类型声明 |

### 3.2 【P0】`dist/` 与 `webui/` 双份：整个正式前端存了两遍

**证据**：
- `git ls-files webui` = **0**；
- `git check-ignore -v webui/index.html` 无输出 → **不是被 ignore，是根本没 add**；
- 与之对照：`dist/` 在 `.gitignore:11`（正常，是构建产物），`config/*.yaml` 全部 tracked；
- 后果：ADR-0017 / 0018 这两份**未提交**的 ADR 描述的正式前端，**在 git 历史里不存在**。最近两次提交是 `b371c3d` / `a25c4e9`（风格榜迁移），而 `scripts/build-webui*.mjs`、`scripts/serve-webui.mjs`、`scripts/verify-webui.mjs` 也全是 `??` 未跟踪。

**要合并什么**：把 `webui/` 与这 4 个脚本**纳入 git**。这不是「重构」，是**把已经生效的正式实现落进版本控制**，风险极低、收益极高。做完之后才有资格谈重构 —— 否则任何重构都是无备份的裸奔。

### 3.4 【P1】探索榜的「筛选」与词库的「筛选」是两套未统一的实现

**证据**：
- 词库侧筛选在 `webui/js/workbench.js:34-51`（`filteredArtists()` / `visibleColours()` / `termCount()` / `colourCount()`），带**分面计数**、组内任一组间全部语义；
- 探索榜侧筛选在 `webui/js/explore-board.js:108-118`（`matches()`），只有 4 个平铺条件，**无计数、无分面、无组内/组间语义**；
- 两者的 URL 契约也不同：词库侧走 ADR-0010 的 hash 契约；探索榜侧的 hash 解析在 Vue 版 `src/utils/exploreHash.ts`（仍被 legacy 引用），静态 WebUI 里**没有对应的独立解析器**，而是塞在 `readHash()` 里只认页签（`workbench.js:60-63`）—— 探索榜的筛选状态**在静态前端里根本没有持久化到 URL**，刷新即丢。

**要合并什么**：把「筛选」抽成**一个引擎 + 一套 URL 契约**（与 ADR-0010 对齐），两个数据源共用。否则每加一个数据源就多一套筛选实现。

### 3.5 【P1】双前端：Vue 版与静态版并存 11,198 行

**证据**：
- `src/` 58 文件 / 11,198 行；`webui/js/` 6 个业务模块 / 2,310 行；
- 两套实现同一批功能：组装（`src/utils/promptBuilder.ts` vs `webui/js/core.js`）、筛选（`src/utils/facetFilter.ts` vs `workbench.js`）、会话持久化（`src/utils/sessionPersistence.ts` vs `core.js:106-208`）、探索榜（`src/components/Explore/*` 5 文件 2,092 行 vs `webui/js/explore-board.js` 440 行）；
- `package.json:11-13` 保留 `legacy:dev` / `legacy:build` / `legacy:preview`，`package.json:28-29` 保留 `verify:legacy`；
- `core.js:135-138` 甚至保留了向 v1 键迁移的兼容代码，注释写「旧前端仍可回退使用」；
- `docs/screenshots/` 4 张截图已与现行静态 WebUI 不符（README.md:76 自述）。

**要合并什么**：删除 `src/` 与 `legacy:*` 脚本。保留成本不只是体积 —— 它让「哪个是权威实现」在每个新人（或未来的我）眼里都要重新确认一次，而且 `verify-app.mjs` 还在维护里。**但这是可逆决策**（`git` 里有历史），风险低于 3.1/3.2。

### 3.6 【P2】词库的两种结构并存：`subCategories` 与直挂 `prompts`

**证据**：`config/prompts.yaml` 的 5 个分类中，`depth-aperture` **没有 `subCategories`**，5 条直接挂在 `prompts` 上；其余 4 个用 `subCategories`。`tools/export-vocab.ts:94-106` 的 `groupsOf()` 为此写了兼容分支（没有子分类就造一个名为「条目」的伪分组）。

**数据后果**：`config/prompts.yaml` 实际生效 **23 个二级分组**，但 `README.md:14` 写「22 个二级分类」；`skills/midjourney-prompt-writing/references/vocab-photography.md` 的总览表 23 行（含伪分组）却与自述的「156 条」对齐 —— 说明伪分组已经污染了下游快照。

**要合并什么**：统一成一种结构（要么都 `subCategories`，要么允许直挂但导出时统一归一），让 `groupsOf()` 的兼容分支退役。

## 四、需重构（什么不合理）

判据：**结构与目标冲突，改架构比改局部更省事**。以下按「改动量 / 收益」排序。

### 4.1 【P0】构建期烘焙全量数据 ↔ 研究需要可查询、可增量、可导出

**冲突本质**：ADR-0003 确立「配置在构建期内联，运行时零请求」，这是「双击即用」的代价 —— 数据在构建期被冻结成静态快照。**但研究工作台的数据是活的**：每天 +200 条作业，研究者要按片段/参数/码聚类、要按时间做 diff、要把结论连同证据导出。

**证据**：
- `webui/js/data-explore.js` = **3.07 MB 单文件**，957 条全量内联；前端 `matches()` 每次全量遍历（`explore-board.js:110`），无索引；
- `data-artists.js` 2.46 MB / 4,322 条 + `data-stylecodes.js` 1.12 MB / 4,638 条 —— 打开工作台要解析 6.68 MB JS；
- 增长推演：每天 +200 条 × 365 天 ≈ **73,000 条**，`data-explore.js` 将膨胀到 **230 MB 量级**，单文件 `<script>` 直接不可用；
- 现有导入是一次性全量载入 + 前端内存过滤（`explore-board.js:108-118`），无增量、无持久化索引、无导出；
- `webui/js/core.js:199-208` 的 `saveSession()` 用 localStorage 存会话 —— **localStorage 容量约 5 MB**，存放研究笔记必然触顶。

**要重构什么**：引入**本地数据层**（Q5 已放宽，仍离线）：
- 作业/拆解/观察记录落到 IndexedDB（或本地 SQLite），构建期只烘焙**种子快照**；
- 筛选下沉到数据层（索引 + 查询），不再前端全量过滤；
- 结论与证据可导出为独立文件（JSON / Markdown）。

**这是最该重构的一处**：它是「生成器架构」与「研究工作台架构」的根本分歧点，其余改动都可以在旧架构内打补丁，唯独这一条不行。

### 4.2 【P0】探索榜是「词库的一个页签」↔ 它在语义上是异质的证据集

**冲突本质**：`CONTEXT.md:124` 与 ADR-0013 把探索榜定为「提示词库的第 9 个页签」，理由是「让会话状态与词库同屏」。但第一性原理上：
- 词库 = **可拼装的片段**（`CONTEXT.md:8-11`）；
- 作业 = **不可拼装的成品**（`CONTEXT.md:128`）。

两者在同一个「提示词库」容器下并列，页签标题「探索榜」与相邻的「快门速度」「艺术家/摄影师」处于同一层级，**暗示它们是同类**，这正是术语模型要防的事（`CONTEXT.md:128` 的 `_Avoid_：作品`）。

**证据**：
- 实际页签是 6 个（`workbench.js:14-19`），`CONTEXT.md:124` 说的「第 9 个页签」与实现不符；
- 探索榜自带独立筛选、独立灯箱、独立收藏、独立拆解展示 —— 它实际是一套**完整应用**，被压成了一张页签；
- Q3 已裁定：社区数据是**证据集**，词库是**假设集**，二者不该同层。

**要重构什么**：把探索榜升为**独立的一级视图**（研究样本库），与词库并列而非从属 —— 两者在「工作台」这一层并列，页签内再分。这同时解决 3.4（筛选引擎统一）与术语冲突。

### 4.3 【P1】更新链的三条入口不一致

**证据**：
- `package.json:20`：`update:explore` = 采集 → 分解 → `build:webui-data` → `build`（**4 步，含重建数据**）；
- `更新探索榜.bat:9/16/24`：采集 → 分解 → `build`（**3 步，跳过 `build:webui-data`**）；
- 后果：跑 `.bat` 会**采集了新数据但前端不更新** —— 新作业进了 `config/explore.yaml`，但 `webui/js/data-explore.js` 还是旧的。ADR-0017:141 已明确记录过这个坑（当时以「15 条新作业会输出 decomposition: null → 灯箱 TypeError」的形式暴露，修复后症状变成了**静默不更新**）；
- 且 `.bat` 的第 2 步 `decompose:explore` 正是 ADR-0017:143 明令禁用的入口。

**要重构什么**：更新链收敛为**唯一一条**（`npm run update:explore`），`.bat` 只做它的薄包装；禁用项从「文档里的禁令」变成「入口不存在」。

**修法与验证（2026-11-10 落地）**：

| 位置 | 改动 |
| --- | --- |
| `scripts/update-explore.mjs`（新增） | 唯一入口：采集 → 分解 → 烘焙 → 构建，四步固定顺序，**失败分级**（采集/烘焙/构建致命，分解只警告不阻断），分解前自动备份、失败自动回滚 |
| `package.json` | `update:explore` 指向编排脚本；新增 `update:explore:no-decompose`（无 LLM 代理时）、`update:explore:collect-only`（只采集，不动产物） |
| `更新探索榜.bat` | 重写为**薄包装**，只 `call npm run update:explore`。流程改动只改一处 |

**为什么必须是编排脚本、不能是 `&&` 链**：

| 需求 | `&&` 能不能表达 |
| --- | --- |
| 分解失败不阻断采集链 | **不能** —— 非零退出即短路，烘焙与构建全不跑 |
| 失败按步骤分级 | **不能** —— 只有一个退出码，区分不出是哪一步、该多严重 |
| 分解失败时回滚派生文件 | **不能** —— `&&` 没有「失败后做清理」的语义 |

**同时解除的 ADR 禁令**：ADR-0017 此前明令 `update:explore` / `decompose:explore` **仍禁**，理由是「会抹掉未提交的精修」。该理由**经复算不成立** —— `writeOutput` 是标准原子写（tmp → 删旧 → rename），失败不留半成品；保留逻辑按 `schemaVersion` + `methodologyVersion` 过滤，实测 **942/942 条一条不丢**（3 手工 + 50 LLM + 889 规则全在）。但「实测没出事」不等于「敢放进每日默认链」，故加了**备份 + 失败自动回滚**两道护栏。

**验证**：

| 项 | 结果 |
| --- | --- |
| 完整四步（`npm run update:explore`） | 采集 971 条 → 分解因缺 `.env` 失败 → **自动回滚** → **不阻断** → 烘焙 971/942/200 → 构建 720 文件 → **退出码 0** |
| `--skip-decompose` / `--collect-only` | 均实测通过；后者 `data-*.js` sha16 **前后完全一致**（产物未被触碰） |
| 回滚完整性 | 派生文件 sha16 `e7b10a24cd3e6130`、942 条、顶层 `model` 完整、**与备份逐字节一致** |
| `npm run verify` / `--dist` | **45/45** / **45/45**（采集后 sref 81→82、比例 35→36，动态断言自动跟随） |
| `npm test` | 10 文件全跑、**135 用例**；1 个 `EPERM` error 经 HEAD 对照跑出**同一形态**，判定为沙箱环境问题（WorkBuddy fs shim），非本步引入 |

**顺带根除的第三个缺陷**：`package.json` 的 `update:explore` 一度写成 `node scripts/update-explore.mnode`（扩展名手误），**不会立刻报错** —— 只有真跑那条命令才暴露；而若直接 `node scripts/update-explore.mjs` 测则**完全绕过**了这条路径。教训：**入口收敛的产物必须从真实入口（`npm run`）验，不能只验被调用的那个文件**。

### 4.4 【P1】参数数据源分裂：`config/parameters.yaml` vs `data-parameters.js`

**证据**：
- `config/parameters.yaml` 10,349 字节，是带版本兼容矩阵的权威源（ADR-0004「版本兼容关系 lives in YAML」）；
- `webui/js/data-parameters.js` 只有 **3 行 / 8,206 字节**，是构建期烘焙的快照；
- 但 `scripts/build-webui-data.mjs` 只处理 explore / decomposed / styles-top 三个输入（`:60-69`），**没有处理 parameters.yaml** —— 说明这个数据文件是**手工同步**的，没有自动化路径；
- 结果：改 `config/parameters.yaml` 后，前端不会自动更新。README.md:21 描述的「按模型版本联动、当前版本不支持的参数自动置灰」是否与 YAML 同步，**没有测试在守**（`tests/` 10 个文件里没有 parameters 的一致性测试，只有 `promptBuilder.test.ts` 测组装规则）。

**要重构什么**：`parameters.yaml` 纳入 `build:webui-data` 的输入，加一条「产物与 YAML 一致」的测试。

### 4.5 【P2】`public/` 与 `webui/assets/` 的图片职责重叠

**证据**：`webui/assets/` 701 文件（12.4 MB），**全部在 `public/` 有同名文件**（实测 701/701）；当前产物走 `../public/` 引用（`data-explore.js` 里 3,828 处 `../public/`），`assets/` 下 48 张是**零引用残留**（`assets/styles-top/` 全部 48 张）。

> **口径更正（2026-11-10 复算）**：本条初稿写「253 张零引用」（`assets/explore` 72 + `assets/styles-top` 48 + `assets/vocab` 133），**该数字有误** —— 判定时用了字面串匹配，而 `assets/vocab/` 是**模板字符串拼接**引用（`webui/js/gallery.js:77` 的 `assets/vocab/${cat.id}/${it.id}.webp` 与 `webui/js/workbench.js:170` 同构），字面匹配查不到。精确重算后：引用 653 / 未引用 **48**。初稿的「253」作废。

**要重构什么**：删掉 `webui/assets/styles-top/` 这 48 张零引用残留（844 KB，当前产物不引用它们）；或让 `build:webui-data` 在 `--images=public` 模式下清理它们。这条**风险最低**，因为产物不引用它们。

**注意**：`assets/explore/` 的 72 张**当前产物同样不引用**（`corpus` 中 `assets/explore` 字面命中 0），但它们是 `--images=sample` 模式的抽样源（`scripts/build-webui-data.mjs:78-92` 的 `sampleSets`），**删掉会让 sample 模式退化为无图**。这一取舍留待第 9 步（`dist/` 单一化）一并裁决，本轮不删。
