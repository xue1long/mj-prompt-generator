# ADR-0024：候选词条作为一级视图 —— 假设集与证据集的对照界面

- **状态**：已采纳（2026-11-11）
- **相关**：ADR-0019（研究工作台定位）、ADR-0020（研究样本库是一级视图）、ADR-0021（对照视图）、ADR-0022（导出与数据层裁决）、ADR-0010（筛选状态写在 URL）
- **来源**：`docs/第一性原理校验报告.md` 第 2.6 节

---

## 背景

报告 2.6 的原文判断是「**词库与社区数据之间零通路**」：

> `config/prompts.yaml` 的 156 条词库与 957 条社区作业是两套互不相通的文本。没有任何代码路径让「社区里高频出现的表述」与「词库里的条目」相遇。

报告提出的补法是「单向通路」：从社区样本抽出**候选词条**（频次 + 出处），人工对照检验后并入词库。词库是待验证的假设集，社区数据是证据集，两者要能对质。

### 实测复核：「零通路」的准确说法是「语义层错位」

按报告字面理解，会以为词库在社区数据里「大量出现但没被引用」—— 补一条通路就能立刻产生价值。实测否定了这个前提。

对比口径：`data-vocab.js` 133 条（`config/prompts.yaml` 156 条减去并入 `data-artists.js` 的 `artists` 分类 23 条）× `phrase-index.js` 抽出的 571 条收录短语（971 条作业，阈值 `MULTI_MIN_DF = 8` / `WORD_MIN_DF = 20`）。

| 口径 | 结果 |
|---|---|
| 精确字符串交集 | **9 条（5.8%）** —— `bright` / `cinematic lighting` / `close-up` / `glossy` / `natural light` / `portrait` / `studio lighting` / `sunlight` / `wide angle` |
| 词元级重合（短语含词库词元） | 146 / 571（**25.6%**） |
| 词库词元从未在社区出现 | 150 / 208 |
| 词库条目零出现 | **71 / 156（45.5%）** |
| 分类覆盖 | `shutter-speed` 0/11、`depth-aperture` 0/5、`artists` 0/23、`lens-position` 3/51、`lighting` 6/66 |

社区 Top 15 高频短语与词库的关系：

| 短语 | df | 状态 |
|---|---|---|
| `background` | 281 | 词库未覆盖 |
| `white` | 265 | 词库有近义 |
| `soft` | 251 | 词库有近义 |
| `black` | 205 | 词库未覆盖 |
| `blue` | 197 | 词库有近义 |
| `light` | 192 | 词库有近义 |
| `warm` | 185 | 词库有近义 |
| `dark` | 183 | 词库未覆盖 |
| `style` | 172 | 词库未覆盖 |
| `hair` | 159 | 词库未覆盖 |
| `green` | 158 | 词库有近义 |
| `realistic` | 154 | 词库未覆盖 |
| `woman` | 154 | 词库未覆盖 |
| `composition` | 153 | 词库未覆盖 |
| `small` | 152 | 词库未覆盖 |

**结论**：词库 156 条是**摄影技术词**（快门 / 景深 / 镜头 / 光线 / 艺术家），社区高频短语绝大多数是**内容词**（背景 / 头发 / 眼睛 / 皮肤）。社区 prompt 说的是「拍什么」，词库说的是「怎么拍」，**两者不在同一语义层**。

这不是「通路缺失」能解释的 —— 把通路接上，也不会让 `background` 变成一条可用的摄影参数。真正的产出是让这件事**看得见**：哪些是词库覆盖到的确认，哪些是方向对但措辞没对上的偏差，哪些是词库结构性的空洞。

## 决定

1. **候选词条是一级视图**，与「提示词库」「研究样本库」「对照」「研究笔记」并列（第 3 个视图，排在「研究样本库」之后，`#candidates`）。
   理由与 ADR-0020 相同：它是**假设集与证据集的交界面**，与两者都不是同层的东西。放进提示词库当页签会暗示「词库的一部分」，而它恰恰是质疑词库的视角。

2. **三态差异标记，不用二值「在 / 不在」**：
   - `exact`（已在词库）—— 整句归一化后相同，或整句**词元集合**与某条词库条目完全相同（词序无关）
   - `near`（词库有近义）—— 至少一个词元在词库中命中，但不是整句等价
   - `missing`（词库未覆盖）—— 词库零重合

   二值会骗人：只看精确命中会误以为词库完全没用（5.8%）；只看零命中会漏掉「词库已有但社区不常用」这类**反向**信号（提示假设集可能过窄或过时）。

3. **全量短语都列出**，不做「只显示 missing」的默认筛选。571 条全在，默认按 df 降序，用户自己筛。理由：默认只显示缺口会让「词库覆盖了什么」变得不可见，而那是判断词库价值的另一半证据。

4. **运行时现算，不烘焙进产物**。候选清单是「由 prompt 推导出来的量」，不是采集来的事实 —— 与 `PHRASE_INDEX` 同一口径。改阈值不用重跑采集、不用重建 6 MB 产物（第 9 步确立的反模式）。

5. **只做候选清单 + 导出，不自动入库、不改词库**。这是单向通路的「阅读端」。是否并入词库是人的判断，代码不做。报告 2.6 说的「人工 / 对照检验后并入」里的「并入」不属本 ADR 范围。

6. **复用 `PHRASE_INDEX` 的抽取算法与阈值，不复刻**。候选来自 `PHRASE_INDEX.build(jobs).phrases`，两处共用同一份抽取逻辑，避免漂移。

7. **出处可回指**。每条候选带 `N 条出处`（引用的作业引用键，去重），点开列出样本，点引用键跳到研究样本库并直达该样本的灯箱（复用 ADR-0013 / 第 6 步的深链机制）。

## 考虑过的选项

| 选项 | 为什么没选 |
|---|---|
| **A. 在提示词库里加一个页签** | 候选词条是质疑词库的视角，不是词库的一部分。放进页签会暗示同层，与 ADR-0020 拒绝「样本库放进提示词库」同一理由 |
| **B. 只显示 missing 的缺口清单** | 丢掉两项关键信息：一是词库覆盖到的确认（12 条 exact），二是「词库有近义但措辞不同」的偏差（136 条 near）—— 后者恰恰是最可操作的改进线索 |
| **C. 二值「在 / 不在」** | 见决定 2 的理由；且 `light blue` 与 `blue light` 这类词序差异会被判成「不在」，而它实际是命中的 |
| **D. 构建期烘焙成 JSON 产物** | 违反第 9 步确立的原则（推导量不落产物）；候选条数与阈值、语料强耦合，烘焙后改阈值要重跑整条采集链 |
| **E. 自动把 missing 并入词库** | 词库是假设集，并入等于让证据自己变成假设 —— 循环论证。人必须看一眼 |
| **F. 独立页面（`candidates.html`）** | 与工作台的一级视图机制重复；`#candidates` 走现有 URL 契约即可，不需要多一个 HTML 入口 |

## 后果

- **正面**：词库的覆盖状况第一次可见 —— 12 条确认、136 条偏差、423 条缺口，三个数字都能导出成文件带走。
- **正面**：`light blue` ↔ `blue light` 这类词序差异被正确识别为命中（词元集合签名口径），不会虚报缺口。
- **正面**：三态 + 全量列出让「词库已有但社区不常用」的反向信号也可见（`shutter-speed` 11 条零出现、`depth-aperture` 5 条零出现、`artists` 23 条零出现）。
- **代价**：候选清单构建有成本（phrase-index ≈ 300 ms + 候选比对 ≈ 390 ms）。已做隔离 —— `viewCount` **不得触发构建**，只有真正进入候选视图才付这笔钱（首页 `count()` 返回 0，实测隔离生效）。
- **代价**：新增 3 个脚本（`candidate-vocab.js` / `candidate-view.js` / `candidate-export.js`），产物从 18 个 JS 增至 21 个。
- **约束**：`minDf` 是**阈值**不是**等值**，不能注册成引擎的 `enum` 维度（enum 语义是精确相等）。它只在 URL 契约层参与（白名单 + 回写），匹配时由视图前置过滤。`'0'` 也不能当「不限」的哨兵 —— 它是真值字符串，会被当成「df 精确等于 0」的激活筛选，把所有候选滤光。用 `''`。

### 实施中踩到的三个坑

| 坑 | 症状 | 根因与修法 |
|---|---|---|
| 跨 vm realm 的 `instanceof Map` | `sourceCount` 全为 0，出处全丢，3 个测试失败 | `Map` 在 vm realm 里创建，跨 realm `instanceof` 必为 false ⇒ `byJobMap` 被替换成空 Map。修法：不用 `instanceof`，用鸭子类型判断（有 `forEach` / `size` 即当 Map 用），或统一 `asMap()` 归一化 |
| `minDf = '0'` 把候选全滤掉 | `.cand-table` 等不到，`matches()` 返回 0 | 见上「约束」条。修法：哨兵改 `''`，阈值前置过滤 |
| `viewCount` 触发重构建 | 首页加载慢 690 ms | `viewnavHtml()` 每次 render 都同步调 `viewCount(v)`。修法：`count()` 只在已构建时给数，构建延到候选视图首次渲染 |

还有一个**非本步引入但由本步暴露**的坑：`verify` 里「不支持的参数有提示」断言原本是「load 之后固定等 700 ms 再查 `.toast`」。toast 只活 1.9 s，而本步新增 3 个 script 标签让 load 事件更晚 ⇒ 断言从偶发失败变成稳定失败。修法不在功能侧，而在断言侧：`openPage` 用 `evaluateOnNewDocument` 先挂 `MutationObserver`（观察目标用 `document` 而不是 `document.documentElement` —— 后者在 document-start 时还是 null），记录所有出现过的 toast，断言不再赌「它现在还在 DOM 里」。
