# 探索榜的展示以作业为单位，四格在卡内与灯箱里都能切

探索榜第一版是**按成图铺网格**：一条作业的四格被拆成四张互不相邻的方图小卡，点任意一格开灯箱，灯箱再把这四格平铺成 2×2。页面上 3768 张图各占一格，用户看不出哪四张是同一个提示词。

## 决定

- **网格按作业聚合**：一条作业一张卡（942 条，不是 3768 张图）。卡片 = 主图 + 标题 + 元信息 + 标签 + **四格缩略图条**。
- **卡片内缩略图条可切主图**：点第 N 格，主图换成第 N 格；这同时修掉了「点了第 3 格，灯箱却不记得」的老问题。
- **灯箱与卡片共用同一套「大图 + 缩略图条」**：灯箱打开时**定位到从卡片点进来的那一格**。
- **主图按作业自己的宽高比显示，不裁切**。卡片容器用 `aspect-ratio` = 作业的声明比例，图片 `contain`。缩略图条也 `contain`，不再裁成方图。
- **灯箱主图不放大**：本地最高只有 640px 档（竖图 640×1144），主图按图片自身尺寸显示，四周留白。宁可留白也不糊。
- **两档图**：`public/explore/thumbs/`（320px，网格与缩略图条）+ `public/explore/mid/`（640px，灯箱主图与下载）。两档都进 dist，保证双击即用。
- **标题 = 提示词前 81 字**，口径与隔壁仓 manifest 的 `title` 一致。
- **下载按钮**下载当前显示的**那一格**，给 640px 档。
- **每批 60 条作业**（= 240 张图），与第一版每次铺 200 张图的加载量相当。

## 考虑过的选项

- **保留成图粒度的网格，只改样式**：改动最小，但四张图在网格里仍然互不相邻，用户依然看不出它们同源——这正是要解决的问题。
- **瀑布流（masonry）排版**：高矮不一的卡片能紧密排列、没有空洞。但 DOM 顺序变成「先往下再往右」，筛选后的阅读顺序不再是「按入队时间倒序」，而这页的价值就是按时间看社区在做什么。所以选 CSS Grid 行内等高，接受行内相邻卡片的文字区高度不齐。
- **灯箱主图用 CDN 的 1024px**：实测浏览器里 `fetch` CDN 一律 **403**（Cloudflare 要 `__cf_bm` cookie，只有真访问过 midjourney.com 的浏览器才有）；curl 能下但那是采集期的事。若要让灯箱用 1024px，只能采集时存本地（3768 张约 950 MB，dist 变 2 GB）。选了 640px（429 MB）这一档，兼顾清晰度与体积。
- **下载按钮跳原站**：不落地、不用存图。但原图 `.png` 直链实测 403，等于按钮是个死链。
- **把作业当提示词条目**：见 ADR-0013，早已排除。

## 后果

- **`public/explore/` 从 63 MB 涨到 492 MB**（320px 63 MB + 640px 429 MB），`dist/` 相应涨到约 700 MB。这是「离线可见 + 灯箱清晰」的直接代价。
- **卡片高度随作业比例变化**：`9:16` 的卡高、`16:9` 的卡矮，同一行内文字区基线会对不齐。这是选「按原比例显示」的必然结果。
- **`ExploreItem` 不再是网格的粒度**：store 直接持有 `ExploreJob[]`，`filteredJobs` 取代 `filteredItems`。筛选条件的语义不变（一直落在作业上）。
- **标题会截断长提示词**：942 条里约 16% 的提示词短于 81 字，其余都会出现省略号。完整提示词只在灯箱里看到。
