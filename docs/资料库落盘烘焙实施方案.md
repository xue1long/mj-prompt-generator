# 资料库落盘 + 烘焙实施方案（方案 ③）

> **状态**：已按 Q1–Q7 推荐默认值实施（2026-11-13）；本文保留为实施清单与决策依据，裁决记录见 [ADR-0030](adr/0030-materials-library-persisted-and-baked.md)
> **原状态**：拟稿 · 待裁决（2026-11-13）
> **来源**：grill-with-docs 第 3 轮；用户指定「③ 落盘 + 烘焙（服务写接口或 CLI）写个实施方案」
> **前置**：ADR-0029 已实现并验证的是「IndexedDB + `blob:`」版。本方案是**替换**它，不是在上面叠加一层同步。
> **边界**：本文件是实施方案，不是已 accepted 的裁决。`CONTEXT.md` / `docs/adr/` / `README.md` 的改动只在第 13 节给拟稿要点，确认后才落盘。

## 0. 一句话

把资料库的**真相源**从「浏览器 IndexedDB」移到「项目文件」：**写**走本机 HTTP 接口（CLI 兜底），**读**走构建期烘焙的 `webui/js/data-materials.js`；`file://` 双击仍可只读浏览，编辑需 `npm run dev`。

不改「双击即用」这件事本身，改的是「双击时能不能写」。

---

## 1. 目标与非目标

| | 内容 |
|---|---|
| **目标** | ① 资料及配图是真实文件，可备份、可 `git`、跨设备靠 clone、清站点数据不受影响；② 回归「配图命名空间唯一 `../public/`」；③ 与研究样本库走同一条 `config/data → 烘焙 → 内联 JS → 静态前端` 主线 |
| **非目标** | 不做云端同步 / 账号 / 多用户协作；不做实时协同编辑；不把资料条目并进 `EXPLORE_JOBS`；不引入 `file://` 下的运行时 fetch |
| **保持** | `dist/` 双击打开仍可浏览全部七个视图；ADR-0022:23「`file://` 下运行时按需读文件被禁」原样成立；`research-store.js` 零改动 |

---

## 2. 第一性原理：为什么切在这一层

| 层 | 内容 |
|---|---|
| 目标 | 数据不因换设备 / 清站点数据而丢，且多设备可继续用 |
| 硬约束 | 数据必须**离开浏览器 origin**，成为用户或项目持有的真实文件 |
| 手段 | 导出包、目录句柄（FSA）、服务写接口、CLI 两段式、云后端 —— 都能满足硬约束，**与有没有 HTTP 服务无关** |
| 系统层才分优劣 | 项目已有单一数据主线 `config/*.yaml → build:webui-data → webui/js/data-*.js → 静态前端只读`。资料库并入这条线 = 单一真相源；留在 IndexedDB + 外部备份 = **第二套平行体系**，长期要自己维护同步、冲突与生命周期 |

**服务只是「浏览器 → 文件」这一步的代劳，不是解。解是「真相源在项目文件里」。**

三条已核实的前提（决定了改动量比直觉小）：

| 事实 | 出处 |
|---|---|
| `npm run dev` / `preview` 从 ADR-0017 起就在，Node 内置 http、零新依赖、只绑 127.0.0.1 | `package.json:7,9`、`scripts/serve-webui.mjs:11-21,282-285` |
| 项目**已有写文件先例**：`serve-webui.mjs:129-215` 的 `/api/settings` 写 `.env`，含 Origin 白名单、字段白名单、8KB 上限、备份 + 失败回退；前端 `core.js:1137,1209-1210` 用 `location.protocol === 'file:'` 做只读降级，verify 有专门断言 | `docs/adr/0022:23` 精确措辞禁的是「同一产物在 `file://` 下运行时 fetch」，**不是**「项目不许有服务」 |
| `/public/**` 已映射到项目根 `public/`（`serve-webui.mjs:239-250`），`../public/...` 在 `file://` 与 http 下指向同一批文件 | 图片零迁移成本 |

## 3. 选定数据流

```
【编辑态 · npm run dev】
 浏览器（http://127.0.0.1:5173）
   │  ① 选清单 + 选图片 / 手工录入 / 补传 / 删改
   │  POST /api/materials/images   { name, dataUrl }
   │  POST|PUT|DELETE /api/materials/items[/:id]
   ▼
 serve-webui.mjs（本机单进程）
   │  ② 校验 → 生成不可控文件名 → 临时文件 + rename 原子落盘
   ├─→ data/materials/items/<id>.json       ← 真相源（文本，入库）
   ├─→ public/materials/<id>_<n>.webp       ← 真相源（配图，入库）
   │  ③ 落盘成功后调用烘焙
   ▼
 scripts/build-materials-data.mjs
   │  读 items/*.json → 校验 → 两阶段验证 → 覆盖写
   ▼
 webui/js/data-materials.js   const MATERIALS_ITEMS = [...]（构建期内联，非运行时 fetch）
   │  ④ 前端 reload / 局部刷新
   ▼
 资料库视图（MATERIALS_VIEW）

【浏览态 · file:// 双击 dist/index.html 或 webui/index.html】
 data-materials.js（随 dist 复制） ──同步 <script>──► 资料库视图【只读】
                                                      导入/补传/删改按钮禁用 + 提示「编辑需 npm run dev」
```

关键：**读路径没有任何 fetch**。烘焙产物用 `<script>` 同步加载，与 `data-explore.js` 完全同构，因此不违反 ADR-0022:23。

## 5. 数据契约

### 5.1 目录布局

```
data/materials/
├── README.md                # 说明：这是真相源，勿手改；编辑请在 WebUI 里做
└── items/
    ├── mat_6f3a….json       # 一条资料条目一个文件
    └── …
public/materials/            # 配图，入库；由服务端生成文件名，客户端不可控
    ├── mat_6f3a…_0.webp
    └── …
webui/js/data-materials.js   # 生成物，勿手改（与 data-explore.js 同级）
```

`.gitignore` 现状 `data/` 整目录被忽略（`:34`），**不解决这条，换设备靠 clone 依然没数据**。改成：

```gitignore
# 本地采集产物不入 git；但资料库是项目一等数据集，必须入库（ADR-0030）
data/*
!data/materials/
```

> `data/*` 忽略直接子项，`!data/materials/` 放行该目录，其下内容无匹配规则 ⇒ 全部入库。
> 不要写成「保留 `data/` 再加 `!data/materials/`」——父目录被忽略时 negation 不生效。
> `public/materials/` 不在现有忽略清单内，默认入库；补一条注释防止将来被 `public/explore/*` 规则误伤。

### 5.2 条目 schema

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | ✓ | 服务端/前端生成，形如 `mat_<时间戳36>_<随机>`；文件名即 `<id>.json`，禁止含路径分隔符 |
| `prompt` | string | ✓ | 原始提示词，去首尾空白后非空 |
| `images` | string[] | — | **仅文件名**（服务端生成），前端拼 `../public/materials/<name>`；可为空数组 |
| `tags` / `author` / `note` | string[] / string / string | — | 可空但保留槽位（Q3 裁决） |
| `source` | `'batch' \| 'manual' \| 'backfill'` | ✓ | 来源，供 5 维筛选复用 |
| `createdAt` / `updatedAt` | number | ✓ | Unix 毫秒；`收录日` 由 `gen-date.js` 同口径换算本地日期 |
| `schemaVersion` | number | ✓ | 恒为 1，为将来字段演进留门 |

**产物侧**（`data-materials.js`）：`MATERIALS_ITEMS`（条目数组）、`MATERIALS_SOURCE`（`{generatedAt, total, withImages, editable:false}`）。图片路径在烘焙时补全为 `../public/materials/<name>`，同时逐条 `imageExists` 校验（复用 `build-webui-data.mjs:115-117` 的思路）。

### 5.3 图片命名与命名空间

- 服务端**忽略**客户端给的原始路径，按 `<itemId>_<seq>.webp` 生成；原始文件名只写进 `note` 或额外的 `originalNames[]`，不参与路径。
- 白名单正则 `^[A-Za-z0-9_-]+$`，命中不了直接 400；`path.resolve` 后再校验前缀仍在 `public/materials/` 内（对齐 `serve-webui.mjs:246-250` 的目录穿越防护）。
- 单一命名空间**恢复**：撤销 `CONTEXT.md:264-267` 的 `blob:` 例外，撤销 `verify-webui.mjs:1339-1341` 对 `blob:` 的豁免。
- `scripts/build-webui.mjs:88-92` 的反向守门要求至少一个 `dist/js/*.js` 含 `../public/` —— 新产物天然满足，构建守门零改动。

### 5.4 去重与冲突合并

- **去重判据不变**（ADR-0029 / Q11）：规范化提示词（trim + 折叠空白 + 小写） + 图片文件名集合（排序）。重复**跳过**并回报条数，不覆盖、不做字段级合并。`MATERIALS_DB.dedupeKey()`（`materials-store.js:165`）移到新模块，算法与单测原样保留。
- **多设备 git 冲突**：一条一文件把冲突面缩到「同一条目同时被改」。约定 `updatedAt` 大者胜；删除用**墓碑文件** `<id>.deleted.json` 而非直接删，避免 A 删 B 改时「改的内容复活」。烘焙时跳过墓碑。
- **本机并发**：Node 单进程事件循环 + 同步 `writeFileSync` 天然串行；仍用「临时文件 `.<id>.tmp` → `renameSync`」保证单文件原子，写入前备份到 `logs/materials/`（复用 `backupEnv` 范式 `serve-webui.mjs:100-106`）。

## 6. 服务写接口契约

### 6.1 路由表

| 方法 | 路径 | 请求 | 响应 | 副作用 |
|---|---|---|---|---|
| GET | `/api/materials` | — | `{ok, editable:true, total, version}` | 无；仅诊断与降级探测，不作数据源 |
| POST | `/api/materials/images` | `{name, dataUrl}` | `{ok, file:'<itemId>_<n>.webp'}` | 压缩 + 写 `public/materials/`；**不触发烘焙** |
| POST | `/api/materials/items` | `{item}` | `{ok, item}` | 写 `items/<id>.json` → 烘焙 |
| PUT | `/api/materials/items/:id` | `{patch}` | `{ok, item}` | 覆写单条 → 烘焙 |
| DELETE | `/api/materials/items/:id` | — | `{ok, id}` | 写墓碑 + 删配图 → 烘焙 |
| POST | `/api/materials/rebuild` | — | `{ok, total}` | 手动补跑烘焙（CLI 兜底用） |

路由分派插在 `serve-webui.mjs:223-228` 的 `if` 之后，形态与 `/api/settings` 一致；`sendJson`(`:58-66`)、`originAllowed`(`:121-127`) 直接复用。

### 6.2 安全与可靠性

| 约束 | 做法 |
|---|---|
| Origin | 复用 `originAllowed()`；`file://` 发不出跨源写，天然隔离 |
| 请求体 | **不复用** `readSettingsBody` 的 8KB 上限（`:56`）——图片 base64 会超。单独设 `MAX_MATERIALS_BODY = 20MB`，超限 413、继续消费流避免挂起（`:112-118` 范式） |
| 字段白名单 | 只收 5.2 的字段，其余静默忽略；`id` / `images` 由服务端改写，客户端传值不采信 |
| 图片校验 | 只接受 `data:image/(webp\|png\|jpeg);base64,`；`sharp` 解码失败即 400，绝不把任意字节写成 `.webp` |
| 路径 | 全链路 `path.resolve` + 前缀校验，禁止 `..`、绝对路径、Windows 盘符 |
| 原子写 | 临时文件 + `renameSync`；批操作（条目 + N 张图）任一失败 → 删本次新增图、不写条目、返回 500 带已回滚标记 |
| 烘焙失败 | 条目已落盘但产物没更新时，返回 `202 {ok:false, needRebuild:true}`，前端提示「已保存，请点重新烘焙」；**不静默假装成功** |

### 6.3 错误码

`400` 字段/格式非法 · `403` Origin 拒绝 · `404` 条目不存在 · `405` 方法不允许 · `413` 体超限 · `500` 落盘/烘焙失败（区分「已回退」与「需手动重建」）· `202` 落盘成功但烘焙未跟上。

### 6.4 dev 与 preview 的模式差异（易漏的陷阱）

| 运行方式 | 服务的页面 | 写接口 | 烘焙产物落点 | 编辑后可见性 |
|---|---|---|---|---|
| `npm run dev` | `webui/` | **开放** | `webui/js/data-materials.js` | 立即（前端内存刷新） |
| `npm run preview`（`--dist`） | `dist/` | **403 拒绝** | 同上，但 `dist/` 是复制产物 | 需 `npm run build` 同步 |
| `file://` 双击 | `webui/` 或 `dist/` | 无（不发请求） | — | 只读 |

烘焙脚本只写源目录 `webui/js/`（`build-webui-data.mjs:38` 的 `OUT_DIR` 就是这么定的）。若在 `preview` 下开放写接口，会出现「盘上数据已更新、但 `dist/` 里的内联 JS 还是旧的」这种最难解释的假象。因此 `handleMaterials()` 在 `useDist === true` 时统一返回 403，提示改用 `npm run dev`。

## 7. 烘焙链

### 7.1 新脚本 `scripts/build-materials-data.mjs`

| 段 | 职责 |
|---|---|
| 读源 | 扫 `data/materials/items/*.json`；**目录不存在 = 空数组，不报错**（资料库允许为空） |
| 校验 | schemaVersion、id 唯一且合法、`prompt` 非空、`images[]` 文件名白名单、墓碑跳过、逐条 `imageExists` |
| 产物 | `render()` 生成 `webui/js/data-materials.js`；banner 注明「生成物请勿手改」与生成时间 |
| 两阶段 | 先 `vm.Script` 语法自检 + 图片存在校验全部通过，再一次性 `fs.writeFileSync`（对齐 `build-webui-data.mjs:233-277`） |
| 报告 | `资料库：N 条 / 有配图 M 条 / 引用 K 张`；`--dry-run` 只统计 |

### 7.2 为什么不复用 `build-webui-data.mjs`

不只因为「每次导入都全量校验 1012 条作业 + 4048 个图片路径太慢」，更因为**契约不同**：

| `build-webui-data.mjs` | 资料库烘焙 |
|---|---|
| `:59-61` 强制三份 config 全齐，缺一即 `process.exit(1)` | 用户数据可以为空、可以目录不存在 |
| `:244/:256` 的校验分支按 `r.jobs` / `r.entries` 二分硬编码，第三类产物会掉进 `else` 报「风格码数不符」 | 需要第三套统计口径 |
| `:262` `must(s.total > 0)`，空数据直接中止 | 空库是合法初始态 |
| 由采集链/人工按天触发 | 每次编辑都要跑，必须快、必须可单域触发 |

代价是 `render()` 模板约 10 行重复。**刻意接受**：把一个「构建期全量校验 + 不杜撰」的脚本改造成「用户可空、高频增量写」的脚本，会污染它原本的守门语义。此偏差写进 ADR-0030。

### 7.3 触发时序

`写盘成功 → spawnSync(node, [build-materials-data.mjs]) → 检查退出码 → 前端按返回值决定「局部刷新」还是「提示重建」`。
前端刷新不做整页 `location.reload()`（会丢筛选状态）：直接读新 `MATERIALS_ITEMS` 需要重新加载脚本，故采用 **`MATERIALS_API.setItems()` 内存替换 + `MATERIALS_VIEW.reload()`**，与现有 `reload()`（`materials-view.js:91-101`）同形态。

## 8. 前端改造清单

### 8.1 双模式判定

```js
const editable = location.protocol !== 'file:' && MATERIALS_API.available();
```

- 主判定用 `location.protocol`（`core.js:1137` 既有范式，零网络依赖）。**注意：`core.js` 没有全局的 `isOffline` / `fileMode` 导出**，`offline` 只是 `openSettingsDialog` 内的局部变量（`:1137`），所以这行判定要自己写，不能指望复用现成函数。
- `GET /api/materials` **只在 http 模式下发**，用于探测「服务在但接口未部署」；`file://` 下一个 fetch 都不发。探测失败一律按只读处理，不弹错误。
- 只读态：`导入资料 / 补传 / 删图 / 删条目 / 编辑字段` 全部 `disabled`，工具栏显示一行「只读浏览 · 编辑请运行 `npm run dev`」。**视图仍完整可浏览、可筛选、可导出** —— 这是与「双击不可用」的本质区别。

### 8.2 `materials-store.js` → `materials-api.js`

| 现有函数（`materials-store.js`） | 去向 |
|---|---|
| `normalizeText` / `normalizeTags` / `basename` / `normalizeImageNames` / `dedupeKey` / `newId` (`:134-169`) | **原样保留**，纯函数、零存储依赖；单测不动 |
| `available` / `open` / `tx` / `toPromise` / `allItems` / `getItem` / `allImages` / `putItem` / `removeItem` / `addImage` / `removeImage` / `clearAll` (`:49-278`) | **删除**，改为 `MATERIALS_API` 的 `load()`（读全局 `MATERIALS_ITEMS`）+ `saveItem()` / `removeItem()` / `uploadImage()` / `rebuild()`（fetch 写接口） |
| `imageObjectUrl` / `releaseObjectUrl` / `releaseAllObjectUrls` (`:281-299`) | **删除**；图片直接 `<img src="…/public/materials/x.webp">`，无对象 URL 生命周期 |

`materials-view.js:92-96` 的 `releaseAllObjectUrls()` + `allImages()` + `imageObjectUrl()` 整段移除，改为从 `MATERIALS_ITEMS[].images` 直接拼路径。

### 8.3 `materials-view.js` 改动点

| 位置 | 改动 |

## 10. 迁移路径（旧 IndexedDB → 新落盘）

1. 本次交付距今极短，判断**尚无真实存量数据**；但不可假设，必须给兜底。
2. 在替换前保留一个一次性入口：`资料库 → 导出完整备份`（JSON 内嵌图片 base64，跨浏览器），由新导入器吃回。这一步可复用 `tests/materials.test.ts` 覆盖的解析逻辑。
3. 迁移完成后：`webui/js/materials-store.js` 删除；`mj-materials` 这个 IndexedDB 库**不主动删除**（浏览器无权替用户清数据），在 README 注明它已成为无引用的遗留库。
4. `data-materials.js` 初始产物为空数组 + `generatedAt`，保证替换当天 `file://` 双击仍能正常渲染空态，不出现「`MATERIALS_ITEMS is not defined`」。
